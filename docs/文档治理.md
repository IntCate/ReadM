# 文档治理与防偏移规则

版本 v0.1。项目文档不是越细越好；细节必须能回答一个实现或验收问题，并有唯一维护位置。

## 权威与状态

用户明确约束高于文档。机器登记 [traceability.json](traceability.json)是需求 ID、阶段、状态和追踪关系的唯一来源；[需求与追踪](需求与追踪.md)是生成视图，禁止独立手改。专业规格维护自己的规则，调研只提供依据；不能用旧研究扩大范围或用详细实现缩小已确认范围。

状态只使用：user-confirmed（用户明确）、proposed-baseline（建议实施基线）、optional（候选）。文档 v0.1 不是产品已发布版本；变更需求含义或阶段时升文档基线并记变更。已实现/已测试由证据记录，不用需求状态替代完成状态。

## 颗粒度准则

| 文档层 | 应包含 | 不应包含 |
|---|---|---|
| 产品 | 用户任务、结果、范围 | 采样器节点、字段与 CSS |
| 交互 | 动作、状态、反馈、错误恢复 | 数据库事务实现 |
| 音乐规格 | 符号、记法、边界 | 多份产品范围表 |
| 数据/命令 | 字段、单位、不变量、原子行为 | 无依据的未来实现 |
| 架构/专项 | 依赖、接口、时钟与匹配契约 | 声称原型性能等于实测 |
| 测试 | 输入、操作、预期、测量条件 | 仅写“功能正常” |
| 计划 | 交付工作包、依赖、出口 | 没有人员依据的精确日期 |

一个需求应有独立可观察结果；当一个工作包超过一个审查单元，实施时拆成子任务，继承需求 ID。不要为了满足一对一形式把共享架构重复写进每个功能文档。

## 唯一维护位置

音乐时值和符号支持只改乐谱规格；实体与文件版本只改数据规范；覆盖/撤销语义只改编辑命令；性能目标和输入限额只改测试文档；设备/音频时钟只改播放与MIDI；匹配和评分只改练习规格；未决项只改风险文档。引用者概述目的并链接，不复制完整规则表。

术语统一：双手=left/right 的演奏归属，谱表=记谱容器，声部=独立节奏线，和弦=同一事件的多个音高；Event 与 Note 不混用；revision 为音乐版本，schemaVersion 为文件结构版本；tie 与 slur 分开；Web 运行在桌面浏览器不等于桌面客户端；跟谱练习不自动等于自由速度跟随。

## 变更流程

1. 登记变更动机和依据，标明来自用户、实验或技术判断。
2. 查需求、规格、数据、用例、工作包和未来兼容性的影响。
3. 更新权威源及相关专业文档；有歧义记录 Q 项，不能私自当确认。
4. 生成需求表并执行检查，人工审查语义冲突、阶段和承诺变化。
5. 记录变更日期、影响 ID、验证结果和未决事项后提交。

新增账号/跨端/格式/高级跟谱功能必须明确加入范围，不能以“预留未来”为由提前开发。若变更会降低双手双谱或三阶段 Web 的已确认要求，必须取得新的用户指示。

## 自动与人工检查

从仓库根运行 `python3 scripts/check_docs.py --write` 更新生成表，然后运行 `python3 scripts/check_docs.py`。脚本检查文档清单、相对文件链接、ID 唯一性、阶段/状态枚举、需求到规格/用例/任务的引用、用例和任务存在性、任务依赖的悬空/循环、登记表是否过期及未登记 ID。

脚本不能证明音乐规则正确、文字没有同义冲突、外链长期有效或实现符合规格。每次跨文档变更仍需逐项人工审查“确认与建议是否混淆、两端规则是否冲突、范围是否悄然扩大、验收是否可操作”。检查报告必须区分静态检查、人工审查与应用测试。
