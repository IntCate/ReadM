# 跨平台音乐软件：产品分析、可行性与技术选型

调研日期：2026-10-18。状态：立项建议，尚未做代码原型、设备实测或用户访谈。已确认需求：第一阶段必须支持双手钢琴谱与双手简谱编辑，不能降级为单旋律首发。三个阶段均先实现 Web；移动端与桌面客户端是已确认的未来需求，当前不实施。文中的工期、性能阈值及商业判断是规划假设，不是已验证结果。默认面向中文用户，以钢琴/MIDI 键盘、个人创作与练习为切入点；默认考虑商业闭源发行。

## 1. 决策摘要

项目可行，但应按“统一乐谱数据 → 双记谱显示与编辑 → MIDI 输入 → 练习匹配”建设。最高风险集中在编辑器与简谱排版、跨端音频延迟、复调跟谱容错，普通业务页面和云服务不是主要难点。

建议当前选型：React + TypeScript + Vite，Web 为三个阶段的唯一交付端；自研乐谱领域模型和编辑命令；VexFlow 承担五线谱绘制，自研 SVG 简谱排版；MusicXML 用于交换；Tone.js/Web Audio 用于播放，Web MIDI 用于键盘接入。PWA 安装及完整离线资源缓存作为可选增强，不能等同于原生客户端支持。

推荐先做 2–4 周技术验证，再冻结依赖版本与浏览器/设备支持矩阵。建议先验收 Windows/macOS 上的桌面 Chrome/Edge；这是实施建议，具体版本由实测锁定。移动浏览器暂不作为完整编辑和 MIDI 验收目标。未来通过平台接口接入移动端、桌面端；Capacitor、Electron、Tauri 暂保留为候选，不冻结为已选方案。

## 2. 产品定位与用户价值

### 2.1 优先服务谁

| 用户 | 核心任务 | 本产品价值 | 优先级 |
|---|---|---|---|
| 初中级键盘学习者 | 看谱、慢速听、分段练习 | 同一首曲子在五线谱/简谱之间切换，逐步过渡识谱 | 最高 |
| 教师及轻量编配者 | 制作练习曲、修改小节、示范播放 | 同一份谱兼顾不同识谱水平，后续接键盘快速录入 | 高 |
| 专业制谱与大型编曲用户 | 复杂总谱、精细出版排版、混音 | 需要大量专业功能，首版不以此为目标 | 后续 |

产品主张建议为：“能编辑、能试听、能接键盘练习的双记谱乐谱工作台。”初期以练习曲、旋律谱和基础钢琴谱形成闭环。

### 2.2 使用闭环

创建/导入结构化谱 → 选择记谱视图 → 修改与试听 → 保存/导出 → 接入键盘 → 分段练习 → 查看错音与节奏记录 → 重练。

当前优先设计桌面浏览器的键鼠编辑体验，响应式布局避免锁死固定屏幕宽度。触摸、平板和手机的完整编辑体验属于未来阶段，不列为当前验收要求。

### 2.3 如何验证需求

立项初期访谈 5–8 位教师和 8–12 位学习者，观察他们完成“8 小节录入、双谱切换、慢速循环播放”。验证：双手简谱编辑是否易用、双手钢琴简谱是否可读；键盘录入是否比鼠标更快；是否愿意持续使用练习反馈。

指标建议：首次完成一份可播放乐谱的比例、8 小节录入耗时、导入后需要修正的比例、练习后再次打开率。先做可用性和留存验证，订阅定价等待真实用户证据。

## 3. 三阶段生产边界

### 阶段一：双谱显示、手动打谱、乐谱播放

必须交付：

- 必须支持钢琴大谱表及左右手简谱的创建、显示和编辑。双手和弦、不同节奏、独立休止及同时播放属于首发核心。建议初始编辑边界为每手一个节奏声部、声部内允许和弦；同一只手多个独立节奏声部的范围仍待明确，数据结构必须支持扩展。
- 常用谱号、调号、2/4、3/4、4/4、6/8 等拍号；休止符、附点、临时升降、和弦、延音线、基本连音线、三连音、弱起与基础反复。
- 音高/时值录入、插入删除、复制粘贴、选区、撤销重做、自动补休止和跨小节拆分延音；明确插入与覆盖两种操作语义。
- 五线谱/简谱切换；同一音符保留稳定身份、选中位置和播放位置。两种视图都允许编辑支持范围内的内容。
- 速度调整、暂停续播、从选中位置播放、A/B 循环、节拍器、左右手静音及光标跟随。
- 本地自动保存、崩溃恢复、项目文件导入导出；MusicXML/MXL 受限子集导入导出，MIDI 导出；打印/PDF 作为可排期的次优先项。
- 对不支持的导入元素生成清单；禁止静默删掉声部、反复或音符。重大不兼容内容允许只读或拒绝导入。

复杂钢琴复调、交叉谱表、装饰音大全、任意出版布局不纳入首版编辑承诺。双手简谱编辑是上线门槛；若排版或编辑未通过验证，必须调整实现或延期上线，不得通过仅保留右手或只读简谱降级交付。

不包含：扫描 PDF/照片识谱、音频转谱、自由演奏自动生成专业谱、实时多人协作、曲谱商城、VST 宿主。PDF 是视觉资料，无法通过普通格式解析获得可编辑的音符。

### 阶段二：MIDI 键盘录入与弹奏

拆成两步发布：

1. **步进录入**：先选时值，再按琴键输入音高/和弦；支持和弦收集窗口、休止快捷键、退格、跨小节延音。MIDI 并不直接告诉软件“这是八分音符”。
2. **有节拍录制**：倒数、节拍器、固定速度、保留原始事件；录完按指定网格量化，手动修正；三连音网格单独选择。自由速度、自动左右手/多声部分离另行研发。

连接与弹奏必须包含设备选择、输入输出端口、热插拔、断连提示、踏板 CC64、力度、卡音清除、音频路由设置。先验证 USB class-compliant MIDI；BLE MIDI 是独立适配项。具备厂商驱动的设备另列兼容范围。

软件发声和电钢琴本机发声要可选，避免双重发声；当前软件监听使用 Web Audio，按音频时钟调度并测量延迟；避免把重排谱面放在发声关键路径。已有琴声时可关闭软件监听，不应强制经过蓝牙音箱。

### 阶段三：MIDI 跟谱练习

按难度发布：

| 子阶段 | 行为 | 技术难度 |
|---|---|---|
| 3A 等待模式 | 弹对当前音/和弦再前进；允许关闭节奏评分 | 中 |
| 3B 节奏模式 | 节拍持续推进，标出错音、漏音、多音、早晚 | 中高 |
| 3C 自由跟随 | 随演奏速度移动，处理插漏音与有限范围重定位 | 高 |

先做分手、分段、慢速、循环。和弦按允许的时间窗口收集；重复音必须依据新 NoteOn，不能用“仍按住”当作再次弹对。等待模式下应区分和弦是否必须同时按住，及是否接受分解按键。

首版评分解释音高、起音节奏与漏音；不根据 MIDI 武断评价指法、音色、美感。踏板使声音延长，不等于手指仍按住；手指释放与踏板释放要分开记录。自由跟随先处理局部错误，任意跳段和复杂装饰音后置。

## 4. 技术可行性与关键约束

| 能力 | 判断 | 主要风险 | 应对 |
|---|---|---|---|
| 跨端普通界面与文件管理 | 可行 | 键鼠/触摸体验与文件权限差异 | 共享核心、适配交互和存储 |
| 结构化谱展示和试听 | 可行 | 格式覆盖、反复展开、时间同步 | 支持清单与标准测试谱 |
| 完整打谱 | 可行但投入大 | 音乐规则与增量布局 | 首版约束记谱子集 |
| 简谱与五线谱转换 | 子集可行 | 多声部、调式、等音拼写、排版 | 统一语义，分视图布局 |
| MIDI 步进录入 | 高可行性 | 设备兼容、和弦边界 | Web MIDI、能力检测与时间戳 |
| 演奏实时转正规谱 | 范围受限可行 | 节奏量化、分声部、自由速度 | 固定速度录制，保留原始数据 |
| MIDI 等待/节奏练习 | 高可行性 | 重复音、踏板、延迟校准 | 确定性匹配与事件回放 |
| 复调自由跟谱 | 需专项验证 | 错误恢复、相同乐句、跳段 | 局部候选、在线对齐/HMM |

### 4.1 双谱切换的实际含义

不是把 C/D/E 的文本替换为 1/2/3。简谱需要约定调号、主音、八度点、减时线、增时线、休止、附点、连音、临时记号、歌词和小节对齐。

默认建议“大调按主音标 1，小调按主音标 6”，并将该记谱策略随项目保存。允许以后切换小调记法；实际发声音高和记谱数字分离。例：同一个实际音高在不同调性下可能显示不同数字，C# 与 Db 的 MIDI 键号相同，但记谱意义不同。

复调、调性频繁变化、无调性音乐可以转换部分音符语义，却不一定生成易读简谱。产品需定义可转换、降级显示与不支持三类结果。MusicXML 的 numeral-root 表示罗马数字/Nashville 和声，不是中文简谱全套排版能力，不能据此认为已有完整简谱支持。[MusicXML numeral-root](https://www.w3.org/2021/06/musicxml40/musicxml-reference/elements/numeral-root/)

### 4.2 MIDI 与浏览器

Web MIDI 不是所有主流浏览器均具备的基础能力，访问还涉及安全上下文和权限。网页中做能力检测，未支持时保留看谱/编辑/播放，并提示切换至经过验证的浏览器；当前没有原生客户端作为补救路径。Safari/iOS Web 不作为 MIDI 首发承诺；支持版本需以发布时兼容表及真机结果锁定。[MDN Web MIDI](https://developer.mozilla.org/en-US/docs/Web/API/Web_MIDI_API)

未来原生端技术备选（当前不实施）：iOS/macOS 可以使用 Core MIDI；Android 可以通过 MidiManager 发现设备，再根据需求使用原生 AMidi 与音频引擎交互。系统 API 存在不代表每个转接头、供电方式与蓝牙设备都通过验证。[Apple Core MIDI](https://developer.apple.com/documentation/coremidi)；[Android AMidi](https://developer.android.com/ndk/guides/audio/midi)

## 5. 当前 Web 选型与未来跨平台备选

当前只实施 React + TypeScript + Vite Web 应用。下表仅保留未来客户端方案比较，不产生当前壳工程或原生插件任务；最终选择应在启动客户端开发时重新验证。以下是结合本项目需求的工程判断，不是框架官方排名。

| 方案 | 优点 | 成本/问题 | 建议 |
|---|---|---|---|
| React/TS + Capacitor + Electron | 直接使用 JS 乐谱生态，Web 是自然目标；桌面 Chromium 环境较统一 | 两种壳；Electron 包体与内存；移动实时音频需原生插件 | 未来候选 |
| React/TS + Tauri 2 | 可覆盖桌面与移动，Rust 适合原生核心 | 系统 WebView 差异、Rust/Swift/Kotlin 维护与音乐适配成本 | 小包体或 Rust 团队时备选 |
| Flutter | 移动与桌面 UI 一致，支持 Web | 使用 JS 乐谱库要桥接或嵌入；自研 Dart 排版增加投入 | 已有强 Flutter 团队可选 |
| React Native + Web/桌面配套 | 原生移动体验，JS 业务复用 | 多端谱面渲染与桌面方案仍要适配 | 移动优先且有 RN 经验时考虑 |
| Qt/C++ + WebAssembly | 原生音乐引擎和桌面编辑能力强 | Web/移动交付、界面和 C++ 成本较高 | 专业制谱团队路线 |

依据：Capacitor 官方目标是 iOS/Android/Web 并提供原生插件接口；Electron 有主进程与 Chromium 渲染进程；Tauri 桌面使用 Windows WebView2、macOS WKWebView、Linux webkitgtk；Flutter 官方支持移动、桌面及 Web，但具体原生能力仍需插件/互操作。[Capacitor](https://capacitorjs.com/docs)；[Electron](https://www.electronjs.org/docs/latest/tutorial/process-model)；[Tauri](https://tauri.app/concept/process-model/)；[Flutter](https://docs.flutter.dev/platform-integration)

选择 React 而非 Vue 不是音乐技术约束；若团队熟悉 Vue 3，可替换 UI 框架而保留领域模型、渲染适配与原生层。当前不建立 Electron、Capacitor 或 Tauri 工程。

## 6. 乐谱引擎与播放技术选型

| 技术 | 实际作用 | 不能直接解决什么 | 选择 |
|---|---|---|---|
| VexFlow | TypeScript 五线谱绘制，SVG/Canvas | 完整编辑器、MusicXML 全量转换、中文简谱、自动分页 | 编辑谱面主选 |
| OSMD | MusicXML 到五线谱的高层展示 | 官方明确不是完整交互编辑器 | 导入预览/对照备选 |
| Verovio | MEI 为核心的排版，MusicXML 输入，SVG/MIDI/timemap 输出 | 产品编辑交互、简谱排版；格式支持有边界 | 出版/MEI 场景备选 |
| MuseScore 引擎/源码 | 成熟制谱软件可作为导入导出对照 | 不是轻量跨端 SDK，集成和许可证需专项处理 | 不作为默认嵌入核心 |
| 自研 SVG 简谱 | 控制中文简谱布局、点击和高亮 | 需建设规则、分页和回归样本 | 必须投入的核心模块 |

VexFlow 官方支持 SVG/Canvas、MIT 许可；OSMD 官方指出频繁移动/插入音符并非其强项。因此推荐用 VexFlow 绘制受支持的编辑内容，自研小节/系统布局和命中测试，而不是让每次按键都重新生成 XML 并整首重排。[VexFlow](https://github.com/vexflow/vexflow)；[OSMD](https://github.com/opensheetmusicdisplay/opensheetmusicdisplay)

OSMD 若用于第一阶段展示，必须置于独立适配层，不把它的内部对象变成项目唯一数据模型。采用两套五线谱渲染器会增加视觉一致性成本，MVP 不必同时上线。Verovio 支持的输出包括 MIDI 和 timemap，但其文档列有时间映射与速度变化约束，仍需验证目标谱例。[Verovio](https://github.com/rism-digital/verovio)；[Verovio 输出说明](https://book.verovio.org/toolkit-reference/output-formats.html)

网页播放推荐 Tone.js + Web Audio，配自有或许可明确的钢琴采样。音乐时间转换由自研 PlaybackPlan 负责，调度器只执行绝对音频时间事件。Tone 官方要求使用回调给出的精确 time 调度音频，普通 setInterval 不应担当发声时钟；屏幕光标从音频时钟推导。[Tone 调度说明](https://github.com/Tonejs/Tone.js/wiki/Transport)

未来原生端研发备忘（不属于当前依赖与验证门槛）：移动端 MIDI 监听发声优先原生：iOS AVAudioEngine/采样器路线，Android Oboe/AAudio + 选定采样器路线。具体采样器须经音色资源、许可证与延迟实测后定；第一阶段普通乐谱试听可先用 Web Audio，但不能据此推断键盘监听体验达标。

## 7. 统一架构与数据模型

```text
React 自适应界面
  ├─ 编辑命令/撤销重做 → ScoreDocument
  │                       ├─ 五线谱布局 → VexFlow/SVG
  │                       ├─ 简谱布局 → SVG
  │                       ├─ MusicXML/MXL 交换
  │                       └─ PlaybackPlan → 音频调度/光标
  ├─ MIDI 适配 → 原始事件记录 → 步进/量化录入 → 编辑命令
  └─ MIDI 适配 → 演奏事件归一化 → 跟谱/评分 → 练习反馈

平台服务：存储、文件、MIDI、音频、时钟、生命周期
可选云端：账号、项目版本同步、练习汇总、资源分发
```

### 7.1 数据原则

- 自有、带 schemaVersion 的 JSON/项目包作为原生格式；MusicXML 是交换格式，MIDI 是演奏事件格式。两者不作为编辑真相源。[MusicXML 规范](https://www.w3.org/2021/06/musicxml40/)
- Score → Part → Staff/Voice → Measure → Note/Rest；每个语义元素有稳定 ID。
- 音高同时保留 step/alter/octave 的记谱拼写、实际发声音高与移调信息；首次只支持非移调钢琴，但结构不要锁死。
- 节拍位置和时值采用有理数，分离音符图形时值、附点、连音比例与实际拍长。浮点秒只在播放边界产生。
- 延音线 tie 与表情连线 slur 分开；延音连接通常合并为持续发声事件，视觉上的音符仍分别存在。
- 保留调号、拍号、速度图、力度、反复/房子、歌词、声部、简谱策略；页面坐标是派生缓存，不写入音乐语义。
- 命令负责音乐规则：拆分跨小节音符、补休止、处理选区和复合撤销；键盘、鼠标、触摸、MIDI 统一调用命令。

### 7.2 两种时间线与两种身份

书面顺序：第 1、2、3 小节；实际演奏顺序可能是 1、2、1、2、3。需把反复展开成多个 occurrence，每个 occurrence 回指相同 scoreElementId，同时拥有独立 playbackOccurrenceId。播放高亮、练习判定、循环和错音统计据此定位，不能用一个小节号唯一代表演奏位置。

原始演奏事件至少记录 deviceId、channel、note、velocity、eventType、单调时钟时间戳和来源时钟标识。当前映射 MIDI 事件时间、performance 时钟与音频时钟，并处理暂停恢复；未来原生适配增加原始接收时间，桥接到达时间不应取代实际事件时间。

### 7.3 存储与后端

第一阶段本地优先：Web IndexedDB；未来原生端可实现 SQLite/文件系统适配，当前不实现；统一仓储接口、自动快照和导出备份。IndexedDB 可能被浏览器清理，应提供持久存储申请及用户可导出的项目包。

有账号同步需求时，建议 Node.js/TypeScript 模块化单体 + PostgreSQL + 对象存储。工程已有 Go/Java 后端可继续使用。服务器不参与实时 MIDI 判断和监听发声。项目用 revision + 乐观并发控制，冲突先产生副本，不以最后写入静默覆盖；实时协作与 CRDT 后置。国内或海外部署按用户地区、发行渠道和数据要求另行选择，不预先锁死云厂商。

当前仓库只建立 apps/web，未来按需增加 apps/desktop、apps/mobile；packages/score-core、editor-core、notation-staff、notation-jianpu、playback、midi、practice、platform-adapters。

## 8. MIDI 练习算法路线

阶段三 A/B 不需要先训练大模型。先把谱编译成按拍分组的目标音集合，使用时间窗口、音高匹配、漏音/多音规则以及设备延迟校准，结果可解释、可回放。

自由跟随再评估窗口化在线动态规划或 HMM：状态包括谱位置、速度估计及候选路径；代价考虑音高、起音时间、插入和遗漏。离线 DTW 本身不能直接保证实时跟随体验。研究已经给出复调 MIDI 跟谱与 HMM 路线，但论文指标不能直接当作本产品达标证明。[复调 MIDI 跟谱研究](https://arxiv.org/abs/1404.2313)；[含装饰音的 MIDI 时序模型](https://arxiv.org/abs/1404.2314)

跟随位置与评分必须分离：算法为恢复位置跳过错误，不代表用户没有漏弹。低置信度时提示用户选择继续位置，避免光标突然跳到重复乐句。

测试数据要包含重复音、柱式和弦、琶音、左右手错开、踏板、错音、漏音、插音、停顿、变速和断连。先采集真实 MIDI 与标注对齐位置，再比较算法；不只用机器生成的完美 MIDI。

## 10. 技术验证与生产验收

### 10.1 先做 2–4 周验证

| 验证 | 样本/设备 | 通过条件（建议） | 失败后的决策 |
|---|---|---|---|
| 双谱编辑一致性 | 20–30 首受控样谱，调号/弱起/三连音/双手/反复 | 支持子集音高、节奏、ID 一致；无静默丢音 | 在保留双手双谱编辑前提下调整记谱子集或渲染适配 |
| 乐谱交互 | 100 小节钢琴谱，基准桌面浏览器及约定屏幕尺寸 | 局部编辑反馈 p95 ≤100ms；高亮不整谱重绘 | 小节缓存、分页虚拟化、减少 DOM |
| MIDI 接入 | Windows/macOS 的目标 Chrome/Edge；至少 3 款 USB MIDI 键盘 | 正确权限、插拔恢复、和弦/踏板；压力回放无应用层丢事件 | 调整 Web 接入实现或收窄浏览器/设备支持清单 |
| MIDI 发声 | USB MIDI + 有线耳机/内置音频 | 目标端到端延迟 p95 ≤30ms，优秀目标 ≤20ms | 优化 Web Audio 调度及音频配置，暂不承诺该组合 |
| 播放同步 | 10 分钟含反复与变速样谱 | 无累积漂移；视听偏差目标 ≤50ms | 修正时钟映射与调度 |
| 跟谱最小闭环 | 单音/和弦/重复音/错误注入 | 等待推进确定；节奏反馈可解释 | 保留等待模式，延期自由跟随 |

这些阈值是待实测的产品目标。MIDI 到界面高亮、MIDI 到声音、音频与视觉偏差是不同指标，不能混为“延迟”。端到端发声用回环/录音测量，只有 JS 日志不足以证明体验达标。蓝牙 MIDI 和蓝牙耳机单列结果，不与 USB + 有线音频合并。

### 10.2 各阶段上线门槛

- 阶段一：支持子集的 MusicXML 往返语义测试、双视图截图回归、撤销恢复、自动保存、反复播放、离线及音频中断恢复通过。交换格式的排版不保证逐像素一致。
- 阶段二：完成设备兼容清单；原始事件与量化结果可对照；断连/切后台/音频路由变化不会持续卡音；NoteOn velocity=0 等常见 MIDI 语义处理正确。
- 阶段三：人工标注集评估逐事件 precision/recall、错漏音判定、位置误差、恢复耗时；不能只报一个总准确率。实际学习者验证误判是否可接受。

MIDI 录入可留到第二阶段上线，但 Web MIDI 接口、时间戳与 Web Audio 监听发声验证应在第一阶段前完成，避免时钟架构到第二阶段返工。当前不验证原生监听链路。

## 11. 人员、工期与成本估算

以下是小团队、基础钢琴范围、无大型曲库/识谱/实时协作的粗估；没有团队背景和验收样谱前，不是交付承诺。

| 工作包 | 建议日历时间 | 主要产出 |
|---|---|---|
| 技术验证与规格冻结 | 2–4 周 | 双谱编辑原型、MIDI/音频实测、支持清单 |
| 阶段一 | 暂按 16–24 周预留 | 双手钢琴谱与双手简谱编辑、试听、Web 发布；原型后重估 |
| 阶段二 | 6–10 周 | 键盘接入、步进录入、有节拍量化 |
| 阶段三 A/B | 8–12 周 | 等待、节奏练习、反馈与记录 |
| 阶段三 C | 另加 8–16 周或更长 | 真实数据驱动的复调自由跟随 |

上述工期沿用此前多端范围的粗估，已不能作为当前 Web-only 交付计划；暂不据此承诺总工期或按比例缩短。技术验证后按编辑器、双谱排版、浏览器 MIDI/音频和练习模块重新估算。自由跟随、复杂复调和出版排版不应被隐藏在同一个 MVP 工期中。

建议 4–5 人核心团队：1 位懂音乐语义的技术负责人、1–2 位编辑器/前端工程师、1 位 Web MIDI/音频工程师、1 位测试/产品设计复合角色；教师或音乐顾问持续参与。若需完整账号后端和运营，再配置相应人力。

此前多端范围下的人月估计不再作为当前预算基线。预算应以 Web 技术验证后的任务估算为准，仍需包含编辑器、音乐规则、双谱排版和真实 MIDI 设备测试；移除原生端任务不会消除这些核心投入。单人实施也必须保留已确认的双手双谱编辑需求。

## 12. 当前建议与需要冻结的产品决定

当前可直接采用的方向：三个阶段仅交付 Web；React/TypeScript 核心与浏览器服务解耦；VexFlow + 自研简谱；结构化 JSON 原生格式 + MusicXML 交换；本地优先；Web MIDI/Web Audio 实现，保留未来原生适配接口；先步进录入再量化录制；先等待/节奏练习再自由跟随。

启动实现前需要冻结：

1. 已确认第一阶段必须支持双手钢琴谱与双手简谱编辑；待明确的是同手多独立声部的首发范围。
2. 简谱的大小调与调号记法；两种视图的可编辑符号范围。
3. 已确认三个阶段先交付 Web；待冻结目标浏览器版本、宿主系统与 MIDI 设备清单；Linux/BLE 是否加入浏览器测试矩阵另定。
4. 现有团队技能、预算和上线目标；是否坚持商业闭源。
5. 是否首版需要账号同步、公开曲库和内容分发。

在这些问题尚未回答时，可先执行技术验证，不应先搭建复杂后端或承诺全格式、全设备支持。
